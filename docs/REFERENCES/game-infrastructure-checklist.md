# 游戏基础设施清单（Game Infrastructure Checklist）

> **用途：** 供 `game-to-issues` skill 在分解 Issue 时读取。
> 确保每次拆解不只覆盖"功能组件"，也覆盖让组件协同工作的"胶水代码"。
>
> **这份文档不假设任何游戏类型或引擎。** 它只定义通用的分解框架。

---

## 核心问题：冰箱里的食物

> 你把所有食材都买齐了，码放在冰箱里。你觉得自己已经"做了饭"。
> 但客人打开冰箱门，看到的不是炖牛肉——是**一堆没切没煮的原料**。

**这就是"只拆组件不拆集成"的后果。** 分解 Issue 时必须区分两类工作：

| | 组件 (Component) | 集成 (Integration) |
|---|---|---|
| **定义** | 一个独立的系统或模块 | 把多个组件连接起来的代码 |
| **可独立测试** | ✅ 是 | ❌ 否（依赖多个组件） |
| **Issue 常见程度** | ✅ 经常被创建 | ❌ 经常被忽视 |

**关键规则：** 每个集成步骤需要一个独立的 Issue。不要默认"组件会自己连接好"。

## 八层基础设施模型

任何可玩的游戏（无论类型）都由以下八层组成：

```
     ┌─────────────────────────────────┐
     │        玩家体验层                │  ← 玩家直接感受到的
     │   (3C + UI/UX + 反馈)           │
     ├─────────────────────────────────┤
     │        交互层                    │  ← 玩家怎么操作
     │   (输入 + 交互可视化)            │
     ├─────────────────────────────────┤
     │        逻辑层                    │  ← 游戏怎么响应
     │   (状态 + 规则 + 条件)           │
     ├─────────────────────────────────┤
     │        内容层                    │  ← 玩家看到/听到什么
     │   (对话 + 叙事 + 音效)           │
     ├─────────────────────────────────┤
     │        场景层                    │  ← 玩家在什么空间
     │   (3D场景 + 碰撞 + 过渡)         │
     ├─────────────────────────────────┤
     │        表现层                    │  ← 游戏怎么呈现
     │   (渲染 + UI + 特效)            │
     ├─────────────────────────────────┤
     │        数据层                    │  ← 游戏怎么存
     │   (存档 + 配置 + 资源)           │
     ├─────────────────────────────────┤
     │        基础设施层                │  ← 游戏怎么运行
     │   (脚手架 + 管线 + CI/CD)        │
     └─────────────────────────────────┘
```

**交互层是最常被完全跳过的层**——人们认为"输入是引擎自带的功能"，但输入系统需要和场景中所有可交互物体通信，这些通信路径在写每个组件时想不到。

## 胶水代码（Glue Code）的定义

胶水代码是让组件之间通信的代码。它通常：
1. 不包含新的"功能逻辑"
2. 不产生新的"游戏内容"
3. **但缺少它游戏就不工作**

**判断一条代码是不是胶水代码：** 如果去掉它，两个独立的组件还在，但它们之间不再通信——游戏功能断裂了。

**晶体代码 vs 胶水代码的类比：**

```
晶体（组件）：独立的、可测试的系统模块
  ─ 对话引擎（能独立加载JSON、渲染选项面板）
  ─ 状态系统（能独立设置/读取数值）
  ─ 场景（能独立当作3D空间加载）

胶水（集成）：晶体之间的连接
  ─ "当对话结束时，解锁玩家移动"
  ─ "当玩家选了一个choice，把scene字段发给SceneManager"
  ─ "当EKeyTrigger检测到玩家进入，注册到PlayerController"
```

**没有胶水，晶体只是一堆零件。游戏是晶体+胶水共同构成的。**

## 集成 Issue 示例（通用）

```json
{
  "id": 24,
  "title": "[Integration] 将交互触发器连接到交互系统",
  "description": "将场景中的所有可交互区域（门、NPC、物体）通过触发器系统连接到玩家的输入系统",
  "context": "当前所有可交互区域只是放置在场景中的静态节点，玩家无法与之交互",
  "acceptance_criteria": [
    "每个可交互区域有对应的触发器节点",
    "每个触发器的信号连接到对应的行为（对话、跳转等）",
    "触发器在玩家进入范围时有可感知的反馈",
    "完整链路能跑通：玩家靠近 → 提示 → 操作 → 响应"
  ],
  "dependencies": [/* 前置组件 Issues */],
  "labels": ["enhancement", "workflow/backlog", "integration"],
  "milestone": "mvp"
}
```

## 集成检查清单

- [ ] 八层模型中有没有被完全跳过的层？
- [ ] 玩家体验链路中有没有"断点"？（玩家做完选择看不到反馈）
- [ ] 每个跨组件的信号/事件/回调是否需要独立的连接 Issue？
- [ ] 如果今天就要跑完整流程，哪些步骤会卡住？
- [ ] 有没有"假设会自己工作"的地方？
