## 2. 设计意图

### 为什么现在做

B5 是 v4 人机共做图谱里 **P0 优先** 的领域（taste-ownership-domains.md：失败即叙事是核心机制，MVP 必开）。「失败」是这个游戏最容易被 agent 写错的领域——默认「失败=惩罚」，而用户的品味是「失败=叙事生产」。本 Issue 在机械槽位（#390/#391）落地前先定文案方向与内容资源 schema，让下游机械实现拿到「统一文本配置」的契约与首批候补值，一次成型。

### 审美坐标与 taste 方向（研究关键发现）

PONG://21 = **雨夜竞技场**（霓虹赛博视觉 #289 落地 + 动态雨幕 #389 + 竖屏攻城肉鸽）。波次转场上下文：「给每波一个清晰的呼吸点与仪式感」；失败屏上下文：「让失败提供信息与氛围，而不是惩罚性界面」。

Obsidian 知识库检索（`/Volumes/Obsidian/Knowledge Ocean/wiki/`，本机已挂载）找到的可迁移设计语言：

| 笔记 | 可迁移到本 Issue 的设计语言 |
|------|---------------------------|
| `极乐迪斯科—概率机制作为叙事语法.md` | **失败生产文学时刻**——「你无法让金尊重你……但你试过了，这比大多数人做的都多」：失败文本不解释失败原因，承认「试过」本身。**失败的类型学**（喜剧/悲剧/知识/道德失败）——失败短句按 severity 分档即类型学的工程化 |
| `跨案例理论综合—14款游戏中的文学性谱系.md` | **失败的四重功能**：机制失败=学习、检定失败=叙事生产、系统失败=涌现叙事、道德失败=伦理凝视——本游戏失败屏 = 「检定失败=叙事生产」+「系统失败=涌现叙事」（拆砖/穿墙数据即涌现叙事） |
| `空洞骑士—沉默作为叙事策略.md` | **少即是多 / 对话是叙事的负空间**——说出的部分远少于未说出的；克制本身是风格：失败短句 ≤10 字、副句 ≤15 字，靠「未说出的」承载情绪 |
| `看火人—对话作为文学的极简实验.md` | 极简叙事的精度：每一处细节服务叙事——副句意象（雨/砖/墙）全部来自游戏已有系统（雨幕/砖墙/波次），不引入陌生意象 |
| `体验引擎-patterns.md` §6 标签化 | 文本=情感标签——副句按波次分档就是给每一波贴一个情感标签（平静→紧迫） |

**taste 方向综合（本 PRD 的注入方向）**：

1. **失败=叙事生产，不是惩罚**：失败短句陈述事实、承认到达（「你打到了这里」），绝不嘲讽、绝不解释「你哪里做错了」（run 数据负责信息）。
2. **世界不因玩家失败而停**：雨继续下（「雨还在下」）——失败不是结局的意象化（对齐 #391「氛围而非惩罚」）。
3. **海明威式克制**：具体名词+动词（砖叠着砖/雨急墙高），删形容词；无感叹号、无 emoji、无网络梗（TASTE.md 风格特征 + #395 同批内容红线）。
4. **随波次推进的张力曲线**（对齐 #367 手感「逐渐加压的紧张感」）：副句从开局的「平静」（雨落无声）走向深段的「紧迫」（墙一层又一层）；失败短句 severity 从「速败的克制」到「攻坚的接近感」（差一点就到 21）。

**开源优先调研说明**（Issue body 要求）：本 Issue 是纯文案内容（文本配置），不涉及粒子/shader/UI 主题/砖块生成等资产类别——Godot Asset Library 与 GitHub 上不存在「文案管理」插件类别；Godot 4.7 内置 `FileAccess` + `JSON.parse_string` 即为文本配置的成熟方案（项目已有 `e2e_shots.json` JSON 配置先例），无需引入第三方依赖。检索结论：无可用插件可复用，自行实现零成本。

## 4. 方案对比

### 4.1 副句风格方向

**Approach A：物象白描——雨/砖/墙三意象（推荐）**

副句只用游戏已有系统（雨幕 #389 / 砖墙 #384 / 波次 #386）的具体物象 + 动词，不引入陌生意象。

- Pros：极简叙事的精度（看火人：每一处细节服务叙事）；意象随波次递进天然形成张力曲线（雨落→砖叠→墙高）；与雨夜竞技场审美零缝隙
- Cons：意象池小，候选易趋同
- Risk: Low ／ Effort: 0.5 天

**Approach B：状态直述**

直接描述当前状态（「难度上升」「敌人变强」）。

- Pros：信息直接
- Cons：**违反海明威式克制**——抽象状态词（难度/强度）是形容词堆砌的变体；把「感受」说破，破坏仪式感
- Risk: Med ／ Effort: 0.5 天

**Approach C：情绪抒写**

「别放弃」「坚持住」类鼓励句。

- Pros：情绪直接
- Cons：**失败=惩罚/说教的变体**（B5 反例）；感叹号高危区；与「克制、不堆特效」的 #391 语境冲突
- Risk: High ／ Effort: 0 天

### 4.2 波次副句候选集合（核心交付：3 档语境 × 2 候选 = 6 条，每条 ≤15 字）

> 依据：PONG://21 波次语义（#386，wave_index 从 1 递增）+ 雨夜竞技场审美 + Obsidian 设计语言（§2）+ 张力曲线（#367 手感）。**research 建议，implement 原样填入 content 资源，用户 2-3 选 1 定稿。**

| # | 语境（第几波） | 候选 A | 候选 B | 情感断言（体验引擎） |
|---|--------------|--------|--------|-------------------|
| 1 | 第 1 波（开场仪式） | 雨落无声 | 第一场雨 | 平静的邀请——雨夜开始，仪式感；「无声」= 负空间（空洞骑士：少即是多） |
| 2 | 第 2-5 波（中段，墙渐厚） | 砖叠着砖 | 雨更密了 | 累积的紧迫——拆砖节奏确立，墙在长高；物象具体、无抽象状态词 |
| 3 | 第 6 波及以后（深段，难度上探） | 墙一层又一层 | 雨急墙高 | 加压的张力——墙厚+雨密双线收紧（对齐 #367「逐渐加压的紧张感」）；「急」为唯一形容词且修饰物象 |

全部 ≤15 字 ✓（最长 6 字）；无感叹号 ✓；无形容词堆砌 ✓（仅「急」1 处且修饰物象）。

### 4.3 失败短句候选集合（核心交付：3 档 severity × 2 候选 = 6 条，每条 ≤10 字）

> severity 判定依据（#391 run 数据：波次/拆砖/穿墙 + 比分差距）：
> - **速败**：第 1-2 波落败、拆砖 0-5（信息量少，短句宜最克制）
> - **鏖战**：中段落败、有拆砖/穿墙数据（失败=叙事生产，承认到达）
> - **攻坚**：深段/比分接近 21（失败=差一点，具体数字）

| # | 语境（失败 severity） | 候选 A | 候选 B | 情感断言（体验引擎） |
|---|---------------------|--------|--------|-------------------|
| 1 | 速败（第 1-2 波，拆砖 ≤5） | 雨还在下 | 墙还在 | 世界照常——失败不是结局（跨案例：失败可重复、是过程而非结局）；零说教 |
| 2 | 鏖战（中段落败，有拆砖/穿墙数据） | 你打到了这里 | 球停雨未停 | 叙事生产——承认到达（极乐迪斯科：失败本身生产文学时刻）；run 数据负责信息，短句负责氛围 |
| 3 | 攻坚（深段/比分接近 21） | 差一点就到 21 | 墙塌了雨没停 | 接近感——具体数字的街机直接（利落不绕弯）；「差一点」= 悲剧失败的轻度变体（情感重量而非挫败） |

全部 ≤10 字 ✓（最长 7 字含数字）；无感叹号 ✓；无 emoji ✓；无惩罚/说教语气 ✓。

### 4.4 内容资源载体

**Approach A：`mini-pong/content/wave_failure_text.json`（推荐）**

新建 `mini-pong/content/` 目录 + 单一 JSON 资源，顶层 `"draft": true`（taste-draft 对白协议：JSON + draft 标记），schema 如下：

```json
{
  "meta": { "draft": true, "domain": "B5", "version": "full" },
  "wave_subtitles": [
    { "id": "wave_open", "context": "第 1 波", "options": ["雨落无声", "第一场雨"] },
    { "id": "wave_mid",  "context": "第 2-5 波", "options": ["砖叠着砖", "雨更密了"] },
    { "id": "wave_deep", "context": "第 6+ 波", "options": ["墙一层又一层", "雨急墙高"] }
  ],
  "failure_lines": [
    { "id": "fail_early", "context": "速败（第 1-2 波，拆砖 ≤5）", "options": ["雨还在下", "墙还在"] },
    { "id": "fail_mid",   "context": "鏖战（中段落败）",           "options": ["你打到了这里", "球停雨未停"] },
    { "id": "fail_deep",  "context": "攻坚（深段/接近 21）",       "options": ["差一点就到 21", "墙塌了雨没停"] }
  ]
}
```

- Pros：AC5 字面要求（独立 content 资源，非代码注释）；#390/#391 用 `FileAccess` + `JSON.parse_string` 直接读取（Godot 4.7 内置，零依赖）；`options` 数组天然实现「2-3 选 1」校准接口（用户定稿 = 把选中项提为 `chosen` 字段或删掉未选项）；diff 友好、review 可读
- Cons：JSON 无注释——语境信息放 `context` 字段而非注释（符合 AC5「不作为注释散落代码」的意图）
- Risk: Low ／ Effort: 0.5 天

**Approach B：Godot `.tres` 资源（Resource 类）**

定义 `WaveFailureText` Resource 脚本 + `.tres` 实例。

- Pros：引擎原生类型安全
- Cons：**过度工程**——纯文案不需要类型系统；需新建 Resource 类 + 注册，把「内容」和「代码」耦合；#390/#391 读取成本更高（需 load 资源类）
- Risk: Med ／ Effort: 1 天

**Approach C：常量散落 / `.gd` 文件**

把文案写在 constants.gd 或各 UI 脚本里。
