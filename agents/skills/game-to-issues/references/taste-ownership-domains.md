# Taste Ownership Domain Map — 人机共做领域图谱 v4

> 来源：用户洞察（2026-07-31）："管线应该有能力做到人机共做——界定好 agent 做什么、人做什么。"
> v3（2026-08-11）：A1/A2 合并为「数值即表达」+ 新增 B5 失败表达。
> **v4（2026-08-11）核心转向：从「门禁」到「队列」。**
> 用户拍板（2026-08-11）："agent 应该生成有我的 taste 方向的草稿，然后创建一个 assign 给我的 issue"——
> **workflow 不该一直等用户**。人的工作 = 显式队列（GitHub Assigned to me），不是散在各 PR 上的隐式闸门。

## 判定框架：什么内容必须人机共做？

三个测试（全通过 = 品味内容，纳入人机共做）：

| 测试 | 问题 | 通过 = 纳入 |
|------|------|------------|
| T1 主观性 | 两个专家会对"好不好"给出不同答案吗？ | 会 → 品味内容 |
| T2 不可断言 | 能写成机器断言（`assert ball.speed == 300`）吗？ | 不能 → 机器测不了"好" |
| T3 语境 | 同样的值换个游戏/场景/情绪还成立吗？ | 不成立 → 依赖人的语境判断 |

T1+T2+T3 全通过 = 人机共做领域。全不通过 = agent 全权（架构、管线、测试、组装）。

> **合并不等于一刀切**：不同游戏类型，数值的校准对象不同（用户确认"不同类型游戏具体标准会不一样"）。

## 核心机制：队列模式（v4，替代 v3 的"校准即验收"）

> **v3 的问题（用户指出）："workflow 一直等我感觉不对"。** 校准即验收 = 门禁——每个 taste-draft Issue
> 的 merge 都等人，人的响应速度绑架管线节奏。
> **v4：人的工作 = 显式队列。** agent 生成带 taste 方向的草稿 → 草稿达标即 merge（结构可用）→
> 同时 assign 给人 + 打 label → 人在方便时处理（攒批）→ close 即定稿。

### taste-draft Issue 生命周期（方案 A：不拆 Issue）

```
1. [Content] Issue 创建 → 正常走 research/plan/implement
2. implement agent 生成「带 taste 方向的草稿」
   （注入: 审美坐标 + Obsidian 笔记 + 项目 docs/TASTE.md 品味档案）
3. review agent 做「定稿就绪检查」:
   结构完整（可编译可运行）+ taste 方向对齐（对照审美坐标/TASTE.md 逐项比对）
   → 不达标打回重写；达标通过
4. 草稿 PR merge 进 main（结构可用）→ 依赖解除 → 下游机械 Issue 立即继续
   同时: assignee=用户 + label=status/human-review（Issue 保持 open，不 close）
5. 用户方便时处理（GitHub Assigned to me = 队列，可攒批）:
   打开 Issue → 微调草稿 → push 定稿 commit/PR → close Issue
6. 定稿改动过 CI → merge；差异记录进 docs/TASTE.md（定稿即反馈）
```

### 关键语义（用户拍板 2026-08-11）

| 语义 | 决定 | 说明 |
|------|------|------|
| human Issue 进依赖链？ | **不进** | 草稿 merge 即依赖满足，下游不等定稿 |
| 机械下游依赖什么？ | **等草稿**（结构先行） | 机械部分不等人的处理速度，定稿后增量替换 |
| 定稿就绪标准 | taste 对齐 + 结构完整 | review agent 检查，达标才 assign 给人（不把烂活丢给人） |
| 品味档案位置 | **项目内 docs/TASTE.md** | 不同项目标准可能不同（用户确认），不跨项目继承 |

### 草稿的「taste 方向」从哪来

```
1. 审美坐标（Grill Me 第零轮产出）— clarified_brief.aesthetic_coordinates
2. Obsidian 笔记（品味证据）— wiki/raw 中与主题相关的设计笔记
3. 项目品味档案 docs/TASTE.md — 历史定稿差异归纳出的方向
   例: "敌视时奉承乘区 0.4→0.3（奉承更廉价）" → 下次同类草稿给 0.3 附近
       "删形容词、短句" → 下次文本草稿按此风格生成
```

### 品味档案格式（docs/TASTE.md，项目内）

```markdown
# TASTE.md — 项目品味档案

> 每次 human 定稿的差异 = 最真实的品味数据。记录方向，不记录绝对值。

## 定稿记录
| 日期 | Issue | 领域 | 草稿值 | 定稿值 | 方向 | 理由 |
|------|-------|------|--------|--------|------|------|
| 2026-08-11 | #42 | A1 | 奉承乘区 0.4 | 0.3 | 奉承更廉价 | 敌视关系里奉承应更卑微 |

## 风格特征（从定稿差异归纳）
- 文本：删修饰、短句、少形容词
- 数值：社交惩罚更狠、奖励更含蓄

## 生成指南（注入 implement agent 的草稿 prompt）
- 数值草稿优先接近最近定稿方向
- 文本按风格特征生成
```

## 与 workflow 对接（v4）

```
game-to-issues 分解时:
  每个 Issue 的 content_ownership: mechanical | taste-draft
  taste-draft 细化到领域: A1(类型标注)/A3/A4/B1/B2/B3/B4/B5/C1...
  taste-draft Issue 的验收条件 = 草稿质量（结构 + taste 对齐），不含"人等"步骤

Grill Me 「校准边界」轮:
  "这个游戏里，哪些簇/领域你想自己掌控？"
  (默认建议: A1 数值 + B1 剧情 + B2 命名 + B3 视觉微调 + B5 失败表达)

implement agent 草稿协议:
  数值 → constants.gd + # DRAFT + 影响注释 + 候补值（朝 TASTE.md 方向）
  对白 → JSON + "draft": true + 风格按 TASTE.md 特征
  失败文本 → 候补清单（2-3 选 1）
  命名 → 候选清单（5 选 1，不直接定）
  视觉 → 截图 + 参数集中在 theme + 拟物/抽象方向标注

review agent 定稿就绪检查:
  taste-draft Issue 草稿达标（结构完整 + taste 对齐）→ 通过
  → 草稿 PR merge → assignee=用户 + status/human-review label（Issue 不 close）
  草稿不达标 → 打回重写，不 assign（不把烂活丢给人）

人车道（队列，非闸门）:
  用户看 GitHub Assigned to me（攒批处理）
  打开 Issue → 微调 → push → close
  差异记录进 docs/TASTE.md → 下次草稿自动朝这个方向

event-processor 依赖语义（需代码改动）:
  _has_unresolved_dependencies: 依赖的 Issue 若带 status/human-review
  且草稿已 merge → 视为依赖满足（human Issue 不进依赖链）
```

## 三个易被忽略的重点

1. **命名/文案（B2）**：成本最低、收益最高的人机接口——玩家第一秒看到的"你的味道"。agent 给候选清单（5 选 1 + 语境说明）而非直接定名。
2. **视觉（B3）**：E2E 截图体系（run-e2e-review.sh + e2e_shots.json）天然就是视觉校准接口。唯一基础设施已就绪的领域。
3. **失败表达（B5）**：最容易被 agent 写错的领域——默认"失败=惩罚"，你的品味是"失败=叙事生产"。候补清单机制让 agent 也能贡献候选，人做最终裁决。

## Obsidian 交叉验证（2026-08-11）

1. **机制参数 = 表达参数**（A1 合并依据）：《极乐迪斯科—概率机制作为叙事语法》《Papers Please—官僚机制作为悲剧结构》《This War of Mine—生存机制作为道德叙事》。
2. **失败即叙事**（B5 新增依据）：跨案例理论综合「失败的类型学」；极乐迪斯科"你无法让金尊重你"——失败生产文学时刻。
3. **视觉语义决策**（B3 细化依据）：raw/Bear/关于游戏UI的思考.md 拟物/抽象/折中三方向。
4. **C4 游戏节奏**：《Before Your Eyes—眨眼机制作为叙事节奏》。
5. **文本密度标准**：Papers Please 笔记中海明威式冰山理论 = B1 的 text_vocabulary 验收锚点。

## 用户偏好（交互方式）

- 用户是资深游戏开发者/文学性 CRPG 审美。校准偏好问题要在 Grill Me 问出来。
- **workflow 不该等用户**（v4 核心）：人的工作 = 显式队列，不是隐式闸门。
- **校准动作必须是低成本的**：试玩剧本 + 候补选项 + 截图，让"微调"而不是"重写"。
- **品味档案在项目内**（docs/TASTE.md）：不同项目标准不同，不跨项目继承。

## MVP 纳入优先级建议

| 优先 | 领域 | 理由 |
|------|------|------|
| P0 | A1 数值（CRPG 型） | 用户点名；constants.gd 已集中；校准即验证表达 |
| P0 | B1 剧情 | 用户点名；对话 JSON 化即可 |
| P0 | B5 失败表达 | 叙事核心 MVP 必开（失败即叙事是核心机制） |
| P1 | B2 命名 | 零成本（候选清单机制），收益最大 |
| P1 | B3 视觉 | E2E 截图已就绪，唯一有现成工具链的 |
| P2 | C1 关卡 | 用户点名；需先建关卡数据格式 |

B4 音效 / C2-C5 等有具体游戏形态再纳入——避免"为了共做而共做"。
